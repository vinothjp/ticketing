# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant SaaS ticketing + project/product-management platform. NestJS + Prisma + PostgreSQL backend (`backend/`), Vite + React + TypeScript frontend (`frontend/`). Despite `Info.txt` describing an aspirational Turborepo/React-Native monorepo, the actual repo is just these two apps plus `docker-compose.yml`.

## Running & building

The app runs via Docker Compose (three long-running containers: `ticketing-postgres-1` `:5432`, `ticketing-backend-1` `:3000`, `ticketing-frontend-1` `:5173`).

```bash
docker compose up          # start everything (backend hot-reloads via nest --watch, frontend via Vite)
docker compose logs backend --tail=20   # check backend compile/runtime output
```

Type-check without Docker (run from the app dir, not repo root):
```bash
cd backend  && npx tsc --noEmit -p tsconfig.json    # note: prisma/seed.ts has pre-existing errors — ignore them
cd frontend && npx tsc --noEmit -p tsconfig.app.json   # NOT -p tsconfig.json — see below
```

**Frontend type-check gotcha:** the frontend's root `tsconfig.json` is a solution file (`"files": []` + project references only). `tsc --noEmit -p tsconfig.json` therefore checks **nothing** and always "passes" — it does not follow references without `--build`. Always use `-p tsconfig.app.json` (or `npx tsc -b`). `tsconfig.app.json` sets `verbatimModuleSyntax: true`, so a type imported as a value (`import { SomeInterface }` instead of `import type`) compiles fine under the useless command but throws a runtime `SyntaxError: does not provide an export named …` in the browser — and since pages are imported eagerly in `App.tsx`, that white-screens the **entire** app, not just the offending page.

Other commands: backend `npm run build` (nest build), `npm run lint`, `npm test` (Jest; single test: `npx jest path/to/file.spec.ts`), `npm run test:e2e`. Frontend `npm run build` (`tsc -b && vite build`), `npm run lint`.

**Dev credentials:** login `admin` / `Admin@123` (tenant admin) or `superadmin` / `SuperAdmin@123`. DB: `postgres` / `password` / db `rbac_db`. Seeded agent users `agent1..agentN` also use `Admin@123`.

## Prisma / schema changes — READ THIS

Migrations are **not** driven by `prisma migrate dev`. The workflow is:

1. Edit `backend/prisma/schema.prisma`.
2. Add a hand-written SQL file under `backend/prisma/migrations/manual/` using idempotent DDL (`ADD COLUMN IF NOT EXISTS`, etc.).
3. Apply it to the running DB: `docker exec -i ticketing-postgres-1 psql -U postgres -d rbac_db < backend/prisma/migrations/manual/<file>.sql`.
4. Regenerate the client and restart so `@prisma/client` types update:
   ```bash
   cd backend && npx prisma generate                     # host copy (for local tsc)
   docker exec ticketing-backend-1 sh -c "cd /app && ./node_modules/.bin/prisma generate"
   docker restart ticketing-backend-1                    # startup also runs `prisma db push --accept-data-loss`
   ```

5. A new column reaches the API only if some service actually selects it. Several services return **hand-built projections** rather than the Prisma model — `customer-companies.service.ts` `list()` and `getOne()` both enumerate fields by hand, so a column added to the schema silently never arrives at the UI until you add it there too. Grep the domain's service for the sibling field before assuming it flows through.

**node_modules gotcha:** containers mount an anonymous `node_modules` volume, so `npm install` on the host does NOT reach the container. After adding a dependency: `docker exec ticketing-backend-1 sh -c "cd /app && npm install <pkg>"` then restart. Host `tsc` will report stale-Prisma-client errors until you run `prisma generate` on the host.

## Multi-tenancy & authorization (core model)

Everything is scoped to a **tenant** (`Client`). Auth is JWT (`@nestjs/passport` + `passport-jwt`); the token payload — and thus `req.user` — carries `{ id, username, roles, clientId, customerCompanyId }`. Services must scope every query by `req.user.clientId`; it is passed down as a `clientId` argument, not inferred globally.

Two user kinds share the `User` table:
- **Internal staff** (`clientId` set, `customerCompanyId` null) — Admins and agents (`Viewer` role).
- **External customer contacts** (`customerCompanyId` set) — belong to a `CustomerCompany` under a tenant, self-serve via `my-*` endpoints.

Roles are strings checked against route metadata:
- `SuperAdmin` — cross-tenant platform admin (global role, `clientId = null`).
- `Admin` — tenant admin.
- `Viewer` — internal agent/technician (ticket/task assignee).
- `CustomerAdmin` — a customer company's own admin (manages their team).
- `Manager` — internal lead. It is a **reporting line, not a right**: it is what the Employee Master's manager dropdown picks from and who an asset request is routed to. Layered **on top of** `Viewer`, never instead of it — every staff gate still reads `Viewer`, and Admin is deliberately not accepted as a manager (that conflation put every admin in every employee's dropdown).

Backend guards in `backend/src/auth/`: `JwtAuthGuard` (authn), `RolesGuard` + `@Roles('Admin', ...)` decorator (role), `TenantGuard` (requires `clientId`), `StaffGuard`, `CustomerAdminGuard`. Frontend mirrors this: `ProtectedRoute` (logged-in) wraps `RoleGate` (role predicates like `isTenantAdmin`, `isCustomerAdmin` defined in `App.tsx`).

**A role's out-of-the-box permissions live in `permissions/default-permissions.ts`** (`DEFAULT_ROLE_PERMISSIONS`, keyed `Role.name` → `AppForm.name`). `PermissionsService.ensureDefaults` seeds them lazily per tenant and is strictly **additive**: it writes only `[role, form]` pairs that have no row at all, so a box an admin unticked on the Roles screen is never restored, and a form the table says nothing about is skipped rather than zeroed. `SuperAdmin` is absent on purpose — it is cross-tenant, so it never appears in a tenant's matrix. Legacy view-only `Viewer` rows from `prisma/seed.ts` were corrected by `manual/viewer_default_permissions.sql`, which rewrites **only** rows still in the untouched seed shape, so an admin's own edit survives.

**The client screens are staff-*readable*, Admin-*writable*.** A named excess-hours approver may be a consultant with no other reason to open a client, so `/admin/customer-companies`, `/admin/clients/:id` and the per-product page are gated `isStaff`, and agents get a Clients nav item. Only four GETs on `api/customer-companies` are opened to `Viewer` (`:id`, `:id/product-contract`, `:id/purchased-products`, `:id/consultants`) — **every write stays `@Roles('Admin')`**, and `/assign` is still Admin-only. Non-admins get no Save/Renew/Assign/delete controls and a `readOnly` `ConsultantGrid`; the tile on the list page routes them to the client instead of opening the admin edit dialog.

- **What a client pays is withheld server-side, not just hidden in the UI.** `contractMonthlyCost` / `amcMonthlyCost` come back `null` for a non-Admin (`hideMoney` threaded through `getContract` / `listCompanyProducts` / `toView` / `contractView`). Hiding the field in a component would still ship the figure over the wire to every agent — keep the check in the service.

## Backend architecture

NestJS, one module per domain under `backend/src/<domain>/` (`tickets`, `projects`, `products`, `customer-companies`, `change-requests`, `kb`, `templates`, `sla`, `timesheet`, `client-visits`, …), each wired in `app.module.ts`. Standard shape: `*.module.ts`, `*.controller.ts` (routes + guards), `*.service.ts` (logic, takes `clientId`), `dto/*.ts` (class-validator DTOs — a global `ValidationPipe({ whitelist, forbidNonWhitelisted })` rejects unknown fields, so every accepted field needs a decorated DTO property).

- **Data access:** `PrismaService` (`prisma/`) extends `PrismaClient` using the **`@prisma/adapter-pg` driver adapter** over a `pg.Pool` — Prisma 7.
- **Uploads:** Multer to local disk under `backend/uploads/{logos,tickets,messages,kb,projects,change-requests}`, served statically at `/uploads`. **`main.ts` never raises the body-parser limit**, so Express's default ~100 KB JSON cap applies — image-sized payloads need a multipart route, not a data URL in a JSON body. (`Product.imageUrl` is a base64 data URL sent via `PATCH /api/products/:id` and will 413 on a large image; don't copy that pattern for new uploads.) Every logo route follows one template — `FileInterceptor('logo')` + `diskStorage` into `uploads/logos`, image-only `fileFilter`, 2 MB cap, store the relative path `/uploads/logos/<file>`, unlink the previous file on replace. See `my-client.controller.ts`, `clients.controller.ts`, `customer-companies.controller.ts`.
- **Cross-cutting services:** `mail/` (nodemailer + per-tenant `SmtpConfig`), `notifications/`, `lib/encryption.ts`. Some services run background sweeps via `setInterval` (e.g. product AMC/warranty expiry).

## Frontend architecture

Vite + React 19 + TypeScript, React Router 7. Routing and role predicates live in `App.tsx`.

- **Server state:** TanStack Query. **HTTP:** a single Axios instance `frontend/src/lib/api.ts` that injects the `accessToken` from `localStorage` and redirects to `/login` on any 401.
- **Auth:** `context/AuthContext.tsx`; base URL is hardcoded in `src/config.ts` (`http://localhost:3000`).
- **UI:** Tailwind CSS v4 + shadcn/ui (Radix primitives) in `components/ui/`, `lucide-react` icons, `sonner` toasts, `react-hook-form` + `zod`. Shared domain widgets (e.g. `ConsultantGrid`, `Layout`, `PermissionMatrix`) live directly in `components/`.
- Pages under `src/pages/`, grouped by area (`tickets/`, `projects/`, `clients/`, `change-requests/`, `super-admin/`, …).

**Dates and times follow the *tenant*, not the browser.** `Client.dateFormat` / `timeFormat` / `currency` (defaults `dd/MM/yyyy`, `HH:mm`, `USD`) are set on the Organization screen from the `DATE_FORMAT` / `TIME_FORMAT` / `CURRENCY` option lists, and every ticket-side stamp renders through `lib/dateFormat.ts`. **Never `toLocaleDateString()`** — it follows whichever machine the user is sitting at, which is not what an organization means when it says its dates are dd/MM/yyyy. The stored value is a **token pattern**, not a locale name (`yyyy yy MMMM MMM MM M dd d HH hh mm ss a`, matched longest-first; anything else is copied through literally), because an admin types it into an editable list — a value added there that isn't in that vocabulary renders as itself.

**Every list screen is the same table.** `overflow-hidden rounded-lg border` wrapper → `components/ui/table` → a `bg-muted/50` header row whose cells are a local `HeadLabel` (a `lucide` icon + a small muted label, `border-r` between columns), values carrying the weight below, bold colour-coded status **pills** (not `Badge`s — see `taskStatusPill` / `statusPill`), and icon-only row actions in a final `w-px` Actions column. It runs across the ticket task grid, `UsersPage`, `RolesPage`, `CustomerCompaniesPage`, `SlaPolicyPage`, `ResourceCostsPage`, `ClientVisitsPage`, `ChangeRequestListPage`, `ProjectListPage` and `ProjectTemplatesListPage`. `HeadLabel` is deliberately copied per page rather than shared — each page's headings differ only by icon — so **match the existing copy when you touch one**; and keep the wide cells `truncate`d with a `title` so no list scrolls horizontally.

**Radix `Select` caveat:** its portalled dropdown does not surface to the automation/browser tooling in this environment — prefer API/DB checks over clicking through a `Select` when verifying. Dropdown lists that must escape an `overflow-hidden` table (e.g. the agent type-ahead) are rendered via `createPortal` to `document.body` with fixed positioning.

**Radix `Select` + async options (bites every edit form):** a controlled `Select` whose `value` is not among its currently-mounted `SelectItem`s gets reset by Radix, which fires `onValueChange('')` and silently overwrites your state. On an edit form that hydrates from a fetched record, the saved value is set *before* the dependent option list has loaded (e.g. product/consultant lists gated on `enabled: !!customerCompanyId`), so the restored value is wiped ~100ms after it lands and the field renders as an empty dropdown. Guard every such handler — `ClientVisitFormPage` uses a `pick()` helper that ignores empty emissions, since a real user selection is never empty. Also give every `SelectValue` a `placeholder`: without one an unmatched value renders as a blank box with no hint anything is wrong. Same trap for any effect that "cleans up" a dependent field — gate it on the list having actually loaded (`isSuccess`), not on `length > 0`, or it clears the value while the list is still empty.

**`RadioGroup` is hand-rolled, not Radix** (`components/ui/radio-group.tsx`): its item calls `onValueChange(value)` on **every** click, including the option that is already selected. Any handler that writes on change must therefore ignore a no-op (`if (v === current) return;`) and must not be live before the true value has loaded — a radio whose `useState` default renders while the fetch is in flight will happily save that default. That is exactly how a client's `contractScope` silently flipped to `PRODUCT`.

**Don't key a hydrate effect on a query's object identity.** TanStack refetches on window focus and hands back a new object each time, so `useEffect(..., [record])` re-hydrates the form and discards whatever the user had typed. Key it on the saved *content* instead (`JSON.stringify` of the fields the form owns, as `ClientDetailPage` does), so a refetch with unchanged data is a no-op and a real server-side change still re-hydrates.

## Business domains

The platform bundles several modules (backend module ↔ frontend page area ↔ main models):

- **Tickets** (`tickets/`) — helpdesk tickets built from admin-designed **Templates** (`templates/`, custom fields in `Ticket.customFields`, keyed by `TemplateField.fieldKey`). **SLA** policies (`sla/`) set response/resolution targets. Picklist option lists (`picklists/`) feed dropdowns — managed on the unified Option List screen (see below).
  - Only `resolutionHours` drives anything: it is what `dueDate` — and therefore every countdown and breach colour — is computed from. `responseHours`, `everyResponseHours`, `operationalHours` (`CALENDAR | BUSINESS`, list in `sla/operational-hours.ts`, mirrored in `SlaPolicyPage`) and `escalationEnabled` are **stored config only** — nothing reads them yet. Don't quote them to a user as if they were enforced.
- **Products & AMC** (`products/`, `customer-companies/customer-products.service.ts`) — see the dedicated section below.
- **Customer companies** (`customer-companies/` ↔ `CustomerCompaniesPage` + `pages/clients/`) — external client organizations under a tenant, their contact users, per-product or one-shared-contract support agreements, and consultant routing. See the dedicated section below.
- **Projects** (`projects/`, `project-templates/`, `project-registers/`, `project-attachments/`, `resources/`, `timesheet/`) — full PM suite: WBS/tasks, sprints, milestones, risks/issues, resources & costs, timesheets, financials (budgets/invoices/expenses), Gantt (`frappe-gantt`).
- **Change management** (`change-requests/` ↔ `change-requests/` pages, model `ChangeRequest`) — the CR module reworked into an ITIL change model. **Labelled "Change Management" in the UI and nav, but every route, directory and API prefix stays `change-requests` / `my-change-requests`** — a UI-only rename, don't "fix" the paths. A record carries ITIL General fields (`changeType`, `changeGroup`, `impact`, `subCategory`, per-record role people) and moves through a **fixed, sequential stage pipeline** — `CHANGE_STAGES` (Submission · Planning · CAB Evaluation · Implementation · UAT · Release · Review · Close) in `change-stage.ts`, mirrored in `changeRequestMeta.ts`; `advanceStage` accepts only the next stage, never a skip or a jump back. **CAB sign-off** (`cabApprovalStatus`) is required for `Major`/`Minor`/`Standard` change types (Emergency exempt) and gates leaving the `CAB Evaluation` stage. The CAB is an **internal Change Approval Board — never the customer** (the customer-admin approval flow below is a separate gate). The approver is a **real staff user**: `ChangeRequest.changeApproverUserId` holds the user id (the authoritative identity `mayDecideCab` checks — that id **or** a tenant Admin), and `changeApprover` is the denormalised full name for display; the CAB-Evaluation stage panel picks the approver from `/api/users` (shown by `User.name`, falling back to username). Two integrity guards: `cabDecision` is only allowed **while at** the `CAB Evaluation` stage (no flipping a decision after the change has advanced), and `changeType` is **frozen once the record passes CAB Evaluation** while any earlier change to it **resets `cabApprovalStatus` to `NONE`** — so a change can't be created Emergency (CAB-exempt), slipped past CAB, then reclassified Major. `User.name` is an optional full-name field (added for this — usernames like `agent1` aren't real names), edited on `UsersPage`. Dependent picklists hang off `ChangeRequestOption.parentValue` (e.g. subcategory→category). The older customer-admin approval flow and budget guard still apply.
  - **A change is raised for a customer or internally** — `ChangeRequest.changeSource` `CUSTOMER` (default) | `INTERNAL`, a radio beside the title. `INTERNAL` **forces `customerCompanyId` and `customer` to null** on both create and update, and `sendForApproval` refuses one outright: an internal change has no customer to approve it. The field is labelled **Customer name**, not customer company.
  - **The General tab is one draggable split, not a tab per stage.** `SplitPane` (`components/SplitPane.tsx`, right column carries the width, divider position persisted in `localStorage`, stacked below `lg`) holds `ContentPanel` on the left — the change's own details, editable at *every* stage — and `StagePanel` on the right, which renders only the open stage's fields and whose primary action is **Move to <next stage>**. Each column saves from a button at its own head. The old per-stage `DevelopmentTab` / `TestingTab` / `DeploymentTab` components were deleted with the stage rename; don't recreate a tab per stage.
- **Client visits** (`client-visits/` ↔ `pages/client-visits/`, model `ClientVisit`, table still `ClientLog`) — logged client visits (`status` `PLANNED` | `VISITED` | `RESCHEDULE_REQUESTED`). See the dedicated section below.
- **Ticket tasks** (`tasks/` ↔ `TasksTab`, model `TicketTask`) — sub-tasks on a ticket, timed by their status trail. Note the module lives at `backend/src/tasks/`, **not** under `tickets/`. See the dedicated section below.
- **Ticket comments** (`comments/` ↔ `CommentsTab`, model `TicketComment`) — threads on a ticket and on its tasks. Also its own module, not under `tickets/`. See the dedicated section below.
- **Employee Master & Asset Master** (`assets/` + the employee columns on `User` ↔ `pages/employees/`, `pages/assets/`, models `Asset` / `AssetAllocation` / `AssetActivity`) — see the dedicated section below.
- **Global search** (`search/` ↔ `components/GlobalSearch.tsx`) — the header search box, `GET api/search?q=`. Guarded `JwtAuthGuard + TenantGuard` only: the **service**, not the route, decides which result types a viewer gets, repeating the visibility rule of the screen each hit links to — tickets for everyone (customer-side users see only their own company's), clients for staff, products and product modules for Admins alone, since the editors they route to are Admin-only. Two-character minimum, 5 hits per type.
- **Knowledge base** (`kb/`), **messaging** (`messaging/` — ticket message threads + channels), **notifications** (`notifications/` + `NotificationBell`), **approvals** (`approvals/`).

**`TicketMessage.isInternal` no longer means private.** The Chat thread (`channel = INTERNAL`, `isInternal = true`) is **shared with the client** — `listMessages` returns the whole thread to everyone who can see the ticket, and the client can post into it. The flag now only separates in-app chat from emailed replies. Don't reintroduce an agent-only filter on it, and don't treat a note written there as hidden.

## Ticket routing & lifecycle (important)

A ticket carries `productId` + `moduleId` + `consultantType` (`TECHNICAL` | `FUNCTIONAL`). On creation for a customer, it auto-assigns a consultant, most-specific-first (see `tickets.service.ts` → `customerProducts.resolveCustomerConsultant`):
1. A **CustomerConsultant** set for that exact product + module + track (client-specific override).
2. Same product+module, any track.
3. **Contract-level default consultant** for the matching track, then a track-less catch-all.
4. Falls back to the product/module's own consultant list only if `Product.autoAssign` is on.

Within any matching group the **primary** (`isPrimary`) agent wins. **Routing is never load-balanced:** a tier is skipped only when it has no consultant for that product/module/track, never because the candidate already holds open tickets — so the same product+module always lands on the same person. `products.service.ts` `firstInOrder()` just takes the head of the `isPrimary desc, sortOrder asc` list; the old `leastBusy()` open-ticket check was removed, don't reintroduce it. Customer-created tickets pass through an **approval gate**: `Ticket.approvalStatus` `NONE` (staff-created) / `PENDING` / `APPROVED` / `REJECTED` (reason required, emailed).

**A ticket holds at most one agent**, though assignment is still the `TicketTechnician` join table: `assignTechnicians` rejects a `userIds` longer than one. Every assign control must therefore be single-select and **replace** the current holder — a checkbox list that appends a second id makes reassignment impossible (that's what broke the ticket-list dropdown, now a `DropdownMenuRadioGroup` with an explicit "Unassigned" row). Who may reassign is gated by *visibility*, not an explicit rule: `StaffGuard` plus `findOne`, so Admins reassign anything and an agent reassigns a ticket they can see — which includes ones they merely hold a task or an approval on, not just ones assigned to them.

**A change of assignee notifies five audiences** (`notifyReassignment`): the incoming agent, the outgoing one, the requestor, the customer company's `CustomerAdmin`s and the tenant `Admin`s. Two guards matter when testing — the **actor is always dropped** (reassign as the only tenant Admin and the "provider admin" leg looks broken), and a re-PUT of the same agent is a no-op that sends nothing. Email goes out as **two** `sendMail` calls so customer and provider addresses never share a `To:`.

**Every status change is stamped, in two places.** `Ticket.statusChangedAt` carries the last move (the detail screen's "In this status since …"), and `TicketActivity` carries the trail. Stamp `statusChangedAt` at **every** door that writes `ticketStatus` — `update()`, `setResolution()`, acknowledge, reopen, approve, both rejections, the auto-close sweep and creation — or the line silently lies on whichever path forgot. Audit summaries quote the tenant's own picklist **labels** via `statusDisplay()`, not raw values; `statusLabel()` is the lower-cased variant for comparing against literals like `'resolved'` and must not be used in text a person reads.

**Resolution → acknowledgement → close, with two tenant-configurable windows** on `Client`, both edited on `OrganizationPage`: `ticketReopenWindowDays` (default 30) and `ticketAutoCloseDays` (default 3). `ticket-auto-close.service.ts` sweeps hourly on a plain `setInterval` (same pattern as `AmcExpiryService`, no external scheduler) and closes resolved tickets the client never acknowledged. Internal tickets — no `customerCompanyId` — are skipped and keep the direct staff close.

**The header bar is one row.** `#number · subject · priority · approval pill` on the left, `Time spent` / `Support hours` chips + Reply on the right, in a `flex justify-between` that does **not** wrap: the subject `truncate`s (with a `title`) and every chip is `shrink-0` + `whitespace-nowrap`, so the figures never drop to a second line on a narrow tab the way they used to. Every hours figure in the bar goes through `n2()` — two decimals at most.

**Ticket detail screen — one green bar, above the tabs.** The resolved/acknowledged state and every action on it live in a single emerald banner in `TicketDetailPage`, rendered above the tab strip so it reads the same on every tab: row one is the status message with **Acknowledge & close** / **Reopen** / the info icon aligned right, row two is `Resolved … · Acknowledged … · Reopened N×` as small muted text (no pill of its own). `ResolutionTab` is the resolution editor only — it deliberately carries no status card and no acknowledge/reopen mutation, just the amber "came back" notice for an unresolved reopened ticket. `ReopenControl` owns the reopen affordance everywhere: button while the window is open, a "Create new ticket" link once it has closed, and the icon alone for staff on a customer's ticket (only the client may reopen theirs — same rule as `TicketsService.reopen`). Don't add a second green bar.

**Every ticket *fact* lives on the Details tab; the overview column carries only the live controls.** The Details tab is one flat card holding a single `sm:grid-cols-3` grid — product/module/type, then template + its template fields, then assigned agent/requester/company — with the project link as a full-width row beneath it. A partially-filled row is ended by `sm:col-start-1` on the next field, which is what stops a template's own fields (however many) from bleeding into the people row; no field sets its own width or offset, or the Assigned agent dropdown shifts its neighbours. The sidebar is **SLA · Status · Priority · Template · Due** and nothing else — the Assigned agent, Project and Template-fields cards that used to sit there were folded into that grid, and the "SLA — Resolve in Nh" row and the "it closes when X acknowledges" hint were deleted as noise.

**One SLA colour scale, one source.** `slaTone()` in `pages/tickets/ticketHelpers.ts` grades remaining time — green until the last quarter of the ticket's own `slaHours`, amber inside it, red overdue (48h fallback), plus a `none` grade for a stopped clock — and `SLA_BADGE_CLASS` / `SLA_PANEL_CLASS` dress it as the list-row pill and the detail countdown panel. `formatCountdown` returns the `tone` with the label. Never re-derive the thresholds at a call site; add a row to the tables instead.

**The SLA countdown card is hidden once the ticket is resolved or closed** (`slaClockRunning` in `TicketDetailPage`). Read it off the live *status meaning*, not the `resolvedAt`/`closedDate` stamps: moving a ticket back out of Closed from the status dropdown leaves those in place, and a ticket that is Open again needs its clock back.

**The tab strip spans the full width.** `<Tabs>` wraps the whole area: `TabsList` first, then the `minmax(0,1fr)` + 18rem/20rem grid *inside* it holding the panels and the overview column. Putting the overview column beside the tab strip instead wraps History onto a second row, and a bare `1fr` takes its minimum from the strip's min-content and pushes the fixed column off-screen.

## Ticket time, tasks & the resolve gate

**`TicketWorklog` is the single source of *billable* ticket time, and it is written on a task's status change — never on a Time tab.** Every screen that quotes hours reads that one aggregate: the Time spent column in the task grid, the ticket header chip, and the customer's support-hours pool (`customerProducts.productSupportHours` → `ticketHours`). It is deliberately an **on-read aggregate, not a stored counter** — deleting a worklog corrects itself. Only `MONTHLY` pools also get a stored write, into `SupportHoursLedger.used` via `adjustLoggedHours`.

- **There is no Time tab and no Log time button.** The one door a consultant enters hours through is the log-time prompt on a task's edit screen (see the task section below), so the figure always sits with the work it was spent on. Every UI gate that used to redirect elsewhere sends the agent to Tasks. `WorklogSection` at the foot of the tab is read-and-delete only, and lists **just the orphans** — entries with no `taskId`, from before tasks existed; it hides itself once there are none.
- **Do NOT mirror the client-visits `drawDown` pattern for ticket hours.** That one increments a stored `hoursUsed`/`contractHoursUsed` counter; adding a second stored counter for ticket time would double-count against the worklog aggregate. Client visits book **visits only** — the hours on a visit are deliberately never charged to the support-hour balance.
- `addWorklog` is the only door in; it and `deleteWorklog` funnel through private `writeWorklog` / `dropWorklog` so the allowance check, the ledger and the "hours low" alert can't drift. The allowance assertion sits in the *caller*, before anything is written.
- A worklog names the task the hours went on: `taskId` + denormalised `taskTitle`, validated to be a task **of that ticket** (still nullable, for the orphans above).
- **Deleting a task deletes the hours booked against it** and credits them back to the customer's pool — `dropWorklogsForTask`, which `TasksService.remove` must call **before** `prisma.ticketTask.delete`: the FK is `onDelete: SetNull`, so once the task is gone there is nothing left to find its worklogs by. The task's own `hoursSpent` is audit-only and needs no second reversal.

**Completing a task is what books its time, and it is confirmed on the task's own edit screen — there is no Start/Stop timer.** Every real change to `TicketTask.status` writes a timestamped `TicketTaskStatusEvent` (server-stamped `at`, `fromStatus`/`toStatus`, denormalised `actorName`). **Three moves have something to collect, and only those open the edit screen**: `DONE` wants the hours the task took, `IN_PROGRESS` on an unassigned task wants whoever is taking it, and leaving `DONE` is a reopen and wants its reason. Every other move — pausing, cancelling, starting an already-assigned task — is written straight from the grid's status pill (`askStatus` in `TasksTab`). A move that needs input is handed to `TicketTaskDialog` as `pendingStatus`: the dropdown shows the queued status, the field that move needs appears inline in the form (the Time spent box in place of Time logged, the reopen reason under Description, the Assignee field ringed), and the **footer's Save** applies it and closes. There is deliberately **no confirm panel** — a bordered box that says "Move to X" and nothing else is a step with nothing in it. `PATCH …/tasks/:id` takes the hours as **`logHours`** and books them through `tickets.addWorklog` (taskId-tagged), **before** the DONE gate reads them and before the status is written — so the hours just entered are what satisfy the gate, and an exhausted pool refuses the whole move rather than settling a task with nothing behind it. Consequences to keep straight:
  - **Time is asked for on completion alone.** Starting, pausing or cancelling a task books nothing — the log-time box does not even render (`asksForTime`), because the figure is what the *finished* task took, entered once, on the way out. Don't reintroduce a prompt on `IN_PROGRESS`.
  - **A task cannot enter `IN_PROGRESS` unassigned.** It may be *raised* unassigned — often is, before anyone picks it up — but starting one waits on an assignee; the trail is a timesheet, and a stretch in progress has to belong to someone. There is **no second picker for it**: the form's existing Assignee field is ringed and carries the hint (and saves on change like every other field there), so there is one control, not a copy to keep in step. `update()` still reads `dto.assigneeUserId` before the stored one, so a caller that sends the assignee and the move in one PATCH works too.
  - **`TicketWorklog` is the only figure any screen quotes, the task grid included.** The `hoursSpent` a task read returns is Σ booked worklog hours for that task (`bookedHours` in `tasks.service.ts`) — so the Time spent column, the ticket header's Time spent, the edit screen's Time logged and the customer's pool are equal by construction. The stored `TicketTask.hoursSpent` column stays derived from the status trail (time the task stood `IN_PROGRESS`) but is **audit only and displayed nowhere**: it is what drifted, because nothing charges it.
  - **`TicketTask.estimatedHours` is create-only.** Typed on **Add task**, read-only on the edit screen, and deliberately absent from `UpdateTaskDto` — the global `forbidNonWhitelisted` pipe rejects it outright — because a figure that can be revised afterwards to match the hours actually spent is not an estimate. It is what the completion prompt is prefilled with, less what is already booked, and is never itself charged to the pool.
  - `logHours` is optional and additive: an empty box books nothing. `hrs()` in `taskMeta.ts` rounds every displayed figure to **two decimals at most**.
  - A **bulk** status move books no time — one figure cannot serve many tasks — so a task with nothing logged is simply refused `DONE` there, exactly as the API refuses it.
  - This **reverts** the Start/Stop timer: `bookRunningStretch`, the Timer column and the live-ticking Time spent are gone. There is no `startedAt`/`endedAt`/`worklogId` column and no `syncTaskWorklog`.

- **Only the task's assignee or a tenant Admin may move its status** (`assertMayTrack`) — the trail is a timesheet. Any agent who can see the task may still edit its title, description, assignee and due date.
- **Leaving `DONE` is a *reopen*, and a different right from running the task**: `assertMayReopen` admits the **ticket's** assignee (read off `TicketTechnician`, not the task's own assignee) or an Admin, and demands a non-empty `reopenNote` saying why. The edit screen therefore asks for a **reason instead of hours** on that one move — the work was booked when the task was closed, so pulling it back open charges nothing — and the bulk Status control excludes completed rows rather than reopening them silently.
- **Only a real transition is recorded.** The status control emits on every pick, including the one already selected; `update()` ignores a re-pick rather than stamping a zero-length event.
- The stored `hoursSpent` column counts closed `IN_PROGRESS` stretches and is never shown; what `list()` / `findOne()` return under that name is the booked worklog total.
- **The Tasks tab is a grid** — Task ID · task · status · assignee · due · Time spent — with a tick column and an Actions column of **Edit** and **Delete**. `taskCode()` renders `TicketTask.taskNumber` as `T-001`; the number is per ticket and assigned **max+1** on create, never a count, so a deleted task's id is never handed to another one. There is deliberately **no Timer column and no Comments column** — comments live on the edit screen, which both the row click and the Edit action open (`TicketTaskDialog`: fields, read-only estimate and time logged, whatever a queued status move still needs, and the thread). Every in-cell control `stopPropagation`s or using it also pops the dialog. **Add task** asks for title, description, estimated hours, due date and assignee.
- **Bulk actions run serially, never `Promise.all`.** Each delete reverses hours against the same month's `SupportHoursLedger` row, and concurrent writes race. The bulk Status control is offered only when the viewer qualifies on *every* selected row (mirrors `assertMayTrack`), and the selection is held as **ids**, so a refetch that reorders or drops a task cannot silently retarget it.

**Resolving or closing is gated three times**, at both doors (`update()` when the status label is resolved/closed, and `setResolution()`): `assertTasksComplete` (no task outside `SETTLED_TASK_STATUSES`), `assertTimeLogged` (Σ worklog hours > 0 — so a task's own hours never satisfy it) and `assertResolutionNotes` (non-empty notes — they are what the client acknowledges and judges a reopen on). All three are **on the way in only**, behind `setResolution`'s `if (!wasResolved)` / `update()`'s `if (!ticket.resolvedAt)` guard, so a ticket resolved before a rule existed stays closable and editing notes on a resolved ticket is never blocked retroactively.

- **Mirror each gate in the UI as a toast on the click, never a standing bar and never a disabled button.** The status dropdown and `ResolutionTab` both pre-check in the same precedence — outstanding tasks, then unlogged time, then missing notes — and redirect to the tab that fixes it. A disabled button explains nothing, and the old permanent amber notices were removed; don't reintroduce them.
- **A task cannot move to `DONE` with nothing booked against it** (`assertTaskTimeLogged`: Σ `TicketWorklog` hours where `taskId` = this task). Because the move's own `logHours` are booked *first*, the figure typed into the prompt is what satisfies it; only a task nobody entered time for is refused. `CANCELLED` is deliberately exempt — work that turned out not to be needed is settled honestly.

- **`TicketTask.status` is `OPEN | IN_PROGRESS | DONE | CANCELLED`**, a plain String column; the list, `SETTLED_TASK_STATUSES` (`DONE` + `CANCELLED`) and the display labels live in `backend/src/tasks/task-status.ts`, imported by both `TasksService` and `TicketsService`. It is its own file precisely so neither import creates a cycle — `TicketsModule` does not import `TasksModule`, so the resolve gate queries `prisma.ticketTask` directly. The frontend mirrors it in `pages/tickets/detail/taskMeta.ts`. **`DONE` reads as "Completed" everywhere a person sees it** — the stored value stays `DONE` (it is what `SETTLED_TASK_STATUSES`, the activity types and every existing row are keyed on), so the wording lives only in those two label maps.
- `CANCELLED` exists so an obsolete task can be settled without faking completion or deleting the audit trail; it keeps the time it had genuinely spent and drops out of `myTasks`.
- `findOne` enriches the ticket with `totalHoursSpent` and `openTaskCount`. Both ride on the ticket itself because the worklog and task endpoints are staff-only — a customer must still see the hours their contract is charged.

## Ticket comments

**One table serves both levels.** `TicketComment.taskId` null is a comment on the ticket; set, a comment on that task. `backend/src/comments/` is guarded `JwtAuthGuard + TenantGuard` **only — no `StaffGuard`**: everyone who can see the ticket can join its thread, customer contacts included, the same reach `messaging/messages.controller.ts` has. Visibility is delegated to `TicketsService.findOne`, which already knows the customer-side rules; the one extra rule the service adds is that **task comments are staff-only**, because tasks are — a customer-side viewer never sees them in `list()` and gets a `403` posting one.

- The **Comments** tab shows the ticket's own thread, then one group per task that has been commented on (empty groups are skipped, or they bury the ticket thread). `TaskComments` is the single thread component both that tab and `TicketTaskDialog` render, and both read one shared `['ticket-comments', ticketId]` cache entry filtered by `taskId` — so a count can never disagree with the list it labels.
- Posting logs a `COMMENT_ADDED` activity entry, so a comment shows up in History with its timestamp.

## Ticket approvals (`approvals/`)

`TicketApproval` is a sign-off asked of one staff user on a ticket. `backend/src/approvals/` is `JwtAuthGuard + TenantGuard`, with `StaffGuard` on every write; visibility rides on `TicketsService.findOne` the same way comments do.

**A ticket approval doubles as an *asset request*.** The row optionally names an asset (`assetId` + denormalised `assetCode`/`assetName`/`assetType`), and **approving one issues that asset** to whoever raised the request, as an `ISSUED` `AssetAllocation` on their Employee Master screen. The asset is optional throughout, so a row without one behaves exactly as the plain sign-off this flow used to be — which is what keeps every approval raised before this existed working. Availability is asserted **twice**: at request time (asking for a laptop that is already out fails while the requester still has the dialog open) and again at decision time *before* the status is written, because the asset may have gone out while the request sat pending — a refusal then leaves the row `PENDING` and still decidable once the unit comes back. Rejecting allocates nothing.

- **Asking and deciding are different rights.** The named `approverUserId` alone may `POST :id/decision`. Editing or withdrawing the request belongs to the side that *asked*: a tenant **Admin or an agent on the ticket's `technicians`** (`loadManageable`, used by `PATCH`/`DELETE api/approvals/:id`). Route guards can't express that — `StaffGuard` alone would let any agent rewrite a request on a ticket they merely can see — so the check is in the service, and the UI mirrors it with `ApprovalsTab`'s `canManage` prop.
- **A column that a viewer can't act in is not rendered at all**, not disabled: the Actions column is mounted only for `canManage`, the Decision column only when the viewer actually has a pending row addressed to them. Edit is offered on `PENDING` rows only — a decided request is a record.
- History gets `APPROVAL_REQUESTED` / `APPROVAL_UPDATED` / `APPROVAL_DECIDED` / `APPROVAL_CANCELLED`; register any new type in `HistoryTab`'s `ICON` map (it falls back to a plain circle).

## Template field ordering (flat, not grouped)

`FIELD_CATALOG` (`backend/src/tickets/field-catalog.ts`) tags every field with a `group` — `ticket_info` | `ticket_detail` | `root_cause`. **That group is a label, not an ordering key.**

The Create Ticket form and the Template Designer's live preview render fields strictly by `TemplateField.sortOrder`, using `groupFieldRuns()` (`frontend/src/pages/tickets/ticketHelpers.ts`) to split the ordered list into *contiguous runs* of the same group and emit one heading per run. Both screens import `FIELD_GROUP_LABELS` from there — don't reintroduce a local `GROUP_ORDER` constant.

- Why: the designer's field list is flat with up/down arrows that save `sortOrder: 0,1,2…`, but both renderers used to re-bucket into a fixed Ticket Info → Ticket Detail → Root Cause sequence. Cross-group reordering was silently discarded (dragging Subject above Priority did nothing, because Subject is `ticket_detail` and Priority is `ticket_info`).
- **Convention: Subject and Description lead the form, then Priority.** They sit at the front of `FIELD_CATALOG` (so they head the "Add system field" list) and of every seeded template.
- Interleaving groups now repeats a heading — that's honest feedback about what the admin built, but keep seeded/default orders **group-contiguous**. `attachments` is a `ticket_detail` field, so it sits with the Subject/Description block rather than at the bottom where it would split that heading in two.
- Existing rows were corrected by `prisma/migrations/manual/reorder_subject_description_first.sql` (idempotent; re-running reports `UPDATE 0`).

## Option lists (one screen for every dropdown)

**Every dropdown list in the platform is managed on a single screen** — `/admin/options` (`OptionListPage`, nav item *Option List*, tenant-admin only). It replaced the separate *Picklist Options* and *Change Mgmt Options* pages; `/admin/picklists` and `/change-requests/options` now `Navigate` to it, and both old page components were deleted. The screen is the registry table (Code · Name · Module · Allow Custom · Values · Active · Actions) over code/name/status/module filters, with each list's values edited in a **Values** dialog (Seq · Code · Description · [Parent] · Active, inline row editing).

**The Module column is a label over the registry, not a second value store.** `MODULES` in `default-lists.ts` — Ticketing · Change Mgmt · Knowledge Base · Projects · Organization · Employee Master · Asset Master — groups the lists by the screen area that uses them, while `source` still decides which table the values live in (Knowledge Base and Organization both write into `PicklistOption`, exactly as Ticketing does). A system list's `module` is derived from `DEFAULT_LISTS`, never typed by an admin, so `ensureDefaults` reconciles it on every load — moving a list between modules is a one-line change there and needs no migration.

The table **paginates client-side** (10/25/50/100 rows, page clamped and reset whenever a filter changes) — the whole registry is one small query, so there is no server-side paging to add.

**Every dialog is capped to the viewport.** `DialogContent` carries `w-[calc(100vw-2rem)] max-h-[calc(100svh-2rem)] overflow-y-auto`, so no dialog can run off the bottom or the sides of the screen; a dialog that wants a pinned header/footer over a scrolling body passes `flex flex-col overflow-hidden` (both Option List dialogs do). Because that box now clips, `date-field.tsx` decides its flip-up against the dialog's bottom edge rather than the viewport's — a `DateField` is the one dropdown here that is not portalled.

**It is a registry, not a third value store.** `OptionList` (`backend/src/option-lists/`) holds one row per list; the values still live where they always did, and every existing dropdown keeps reading its own endpoint unchanged:

- `source = PICKLIST` → `PicklistOption`, via `api/picklist-options` (tickets, templates, KB).
- `source = CHANGE_REQUEST` → `ChangeRequestOption`, via `api/change-requests/options` (Change Management).

`OptionListsService` proxies value CRUD to whichever table `source` names, mapping the screen's `code`/`description`/`seq` onto the tables' `value`/`label`/`sortOrder`. So a value added on this screen is live in the ticket form immediately, and **no consumer, seed or route had to change** — don't "finish the job" by migrating the two tables into one.

- **`DEFAULT_LISTS` (`option-lists/default-lists.ts`) is the one registry of known lists**, seeded lazily per tenant by `ensureDefaults` (idempotent; it only adds what's missing, so a rename or a deleted value is never overwritten). It also calls `CrOptionsService.ensureDefaults`, which is why `ChangeRequestsModule` exports that service. The frontend's old `CR_OPTION_LISTS` and the picklist page's `LISTS` constants were removed — add a new list here, not in a component.
- **A seeded list is `isSystem`:** renameable and its values fully editable, but it **cannot be re-coded or deleted** — application code looks it up by `listKey` (`'ticketStatus'`, `'priority'`, `'change_type'`…). Both guards live in the service, and the UI mirrors them (disabled trash with a title, fixed Code field). A **custom** list keys its values off its own code, so re-coding one moves its values with it (one transaction) and deleting one deletes them.
- **A list belongs in the registry only if a field reads it *and* no other screen owns the records.** A dropdown that names a template, project, product module, user or customer is not an option list: those are created and managed on their own screens, and a name typed into a list here could never become the record it names. The CR fields that used to work that way (`person`, `project`, `module`, and earlier `customer`) now read the real records through **`EntitySelect`** (`pages/change-requests/OptionSelect.tsx`) — same stored string, so existing records read back unchanged and a stored name no longer matching a live record is still shown. `TEMPLATE_CATEGORY` was registered and then retired for the same reason; template categories stay in `templateMeta.ts` with the Templates screen that owns them.
- **A list belongs in the registry only if a field actually reads it.** Every dropdown in the app was audited against that rule:
  - Registered beyond the five the old picklist screen managed: `requestType`, `kbModule`, `kbCategory`, `kbSubCategory` (seeded data that had no admin screen at all), plus four lists whose values were **hard-coded arrays in a component** and are now admin-editable, all under the Projects module — `expenseCategory` (project expense), `timesheetActivity` (the timesheet Activity column), `projectDocumentType` (Documents tab) and `projectInvoiceType` (invoice commercial model).
  - **Retired** (`option_list_prune.sql`, registry rows only — the values stay, so re-registering brings them back): `RESOLUTION_CODE` (`Ticket.resolutionCode` has no DTO, no writer and no UI), and `CHANGE_CUSTOMER` / `CHANGE_PROJECT` / `CHANGE_MODULE` / `CHANGE_PERSON` / `TEMPLATE_CATEGORY` under the records-another-screen-owns rule above. The dead `CR_OPTION_LISTS` constant went with them.
  - **Deliberately still hard-coded**, because code branches on the literals — an admin edit would change behaviour, not wording: ticket task statuses, project/task/milestone/sprint statuses and WBS types, client visit statuses, change stages and `CAB_TYPES`, KB `articleType`/`status`/`audience`, consultant track, message channel, approval states, SLA operational hours, project priority. The list is repeated in `default-lists.ts` so nobody "finishes the merge" by mistake.
- **A list that replaced a hard-coded array carries `defaultValues`**, seeded by `ensureDefaults` only into a list with no values at all — the seed must reproduce the old array exactly or existing records stop matching it. Their consumers read the list through `useOptionValues(listKey, FALLBACK)` (`frontend/src/lib/optionLists.ts`) and keep the old array as the fallback, so the options are never briefly empty (an empty option set is what makes a controlled Radix `Select` drop its saved value).
- **`components/PicklistSelect.tsx` is the shared dropdown for a `PicklistOption`-backed list** (the CR store's twin is `OptionSelect`). It maps empty to a `__none__` sentinel, since Radix cannot hold an empty value, and **still renders a stored value that is no longer in the active list** — otherwise Radix treats it as unmatched, resets it and wipes the field on the next save of any record written before a value was renamed or deactivated.
- **Timesheet activities are the one case with a server-side gate.** `SaveRowDto.activity` no longer carries `@IsIn(TIMESHEET_ACTIVITIES)`; `TimesheetService.activityList()` reads the tenant's `timesheetActivity` list (falling back to the seeded array) and `saveWeek` rejects anything outside it, which is also what the week response and the Excel import match against.
- **`OptionList.allowCustom` and `OptionList.isActive` are stored config** — nothing reads them yet; don't quote them to a user as enforced. A *value's* `isActive` is the live one, as before.
- Dependent lists carry `parentListKey` (the parent list's `listKey`, matching the values' `parentValue`): `TICKET_SUB_CATEGORY`→`ticketCategory`, `KB_SUB_CATEGORY`→`kbCategory`, `CHANGE_SUB_CATEGORY`→`category`. `GET :id/parent-values` feeds the dialog's Parent dropdown, and the column/field only appear for such a list.

## Products / consultants / coverage model (the area with the most churn)

- **`Product`** → has **`ProductModule`**s (`ProductModule.tracks[]`, default `[TECHNICAL, FUNCTIONAL]`) or, when unsplit, product-level tracks. Each module/track has an ordered consultant list (**`ModuleConsultant`** / **`ProductConsultant`**, `isPrimary`, `sortOrder`). Grid columns everywhere are **Technical / Functional / Others**; custom/other tracks map to the *Others* column (stored as `track = null`).
- **`CustomerCompanyProduct`** — a customer's purchased product on ONE coverage timeline chosen by radio: **Warranty (free) → AMC (paid)**. `amcType` `FREE` = under warranty, `PAID` = under AMC; `freeAmc*` fields hold the warranty pool, `paidAmc*` the AMC pool. Terms are a date range + support hours + visits (+ contract amount for AMC). `amc-expiry.service.ts` runs periodic sweeps for expiry/alerts.
- **`CustomerCompany.contractScope`** `PRODUCT` (per-product AMC) vs `CUSTOMER` (one shared pooled contract; `contractCoverageType` `WARRANTY` | `AMC`, shared dates/hours/visits). The client screen has a Per-product / One-customer-contract radio, and the customer-contract form carries the same Warranty/AMC radio as the per-product screens.
- **Warranty is free, so it never carries a contract amount.** All three coverage screens (`ClientDetailPage`, `ClientProductPage`, `ClientAssignProductPage`) hide the Contract amount / Monthly cost field unless coverage is `AMC`, and `setContract` / `renewContract` force `contractMonthlyCost` to `null` for `WARRANTY` regardless of what the caller sends — so switching AMC → warranty clears a stale amount.
- **`CustomerConsultant`** — the client's own consultant assignments (per product+module+track, or contract-level with `productId=null,moduleId=null`), with `isPrimary`. The contract-level rows are the client's **Default consultants**: one shared set that applies whatever the `contractScope` is, so `ClientDetailPage` renders that grid in **both** modes (it used to be gated to `CUSTOMER`). Per-product overrides stay on `ClientProductPage`. These are **independent** of the product's `ModuleConsultant`s: assigning a product does NOT auto-copy the product's consultants (there is deliberately no `seedConsultantsFromProduct` — it was removed); removing a product deletes its `CustomerConsultant`s so a re-add starts clean.
- **Switching `contractScope` is guarded, and confirming the dialog is what applies it.** On `ClientDetailPage` the Contract type radio stays disabled until the saved contract has loaded, ignores a re-pick of the current value, and confirms either direction in a dialog. Confirming PUTs `{scope}` on its own, in **both** directions — no second **Save contract** press. That is safe because `setContract` is a **partial** update: a field the payload omits is left as it is, and only an explicit `null` clears it (it used to null `contractStart`/`contractEnd`/`contractVisits` on any CUSTOMER write, and to demand a support-hours pool a fresh client didn't have). Two consequences: the support-hours pool is re-resolved only when `hoursUnlimited`/`hours` is actually present, and `saveCustomer` must send `null` — never `undefined` — for a box the admin emptied, or the clear is silently dropped. `productIds` was already opt-in; an absent list leaves the covered products alone, while an empty one still means "covers nothing".
- **The customer-contract screen mirrors the per-product one.** In `CUSTOMER` scope `ClientDetailPage` shows Products covered (with its own **Assign a product** button) full-width, then read-only **Coverage** left and editable **Terms** right; per-product it is `ClientProductPage`. Both render the same three meters through `components/CoverageMeter.tsx` — coverage term, support hours, site visits — whose `pct` is the share **consumed** (`contract.period.pct` is percent elapsed, pass it straight through). `ClientAssignProductPage` hides its per-product terms under `CUSTOMER` scope and posts only `productId`, since those pools are never read there.
- **How a support-hours pool is *counted* is configured per client, and applies to both scopes.** Six settings, mirrored field-for-field between `CustomerCompany` (`contract*`) and `CustomerCompanyProduct` (`amc*`): `…HoursPeriod` `FULL_AMC | MONTHLY`, `…CarryForward`, `…AllowTicketsAfterHours`, `…AllowExcess`, `…ExcessApproval`, `…ExcessApproverId`. `resolvePoolConfig()` collapses that pair into one shape, so service code never branches on scope. The whole block is one shared UI widget, `components/SupportHoursConfig.tsx` — edit it, not per-screen copies. It is a `divide-y` list of label-left / control-right rows, sits in the **Support hours settings** card beside **Terms** (`items-stretch` + `h-full` + `mt-auto` on Save, so the two columns end on the same line), and takes `readOnly` for non-Admin staff instead of hiding: every staff member reads a client's terms, only an Admin writes them, and the excess decision below stays live regardless.
- **`MONTHLY` pools keep a per-calendar-month ledger** (`SupportHoursLedger`, unique on `[scope, ownerId, periodLabel]`, holding `allocated` / `carriedIn` / `used`). The month's cap is `allocated + carriedIn`, and `carriedIn` is only non-zero when carry-forward is on. `rollForwardLedgers()` opens the new month's bucket, called from the `amc-expiry.service.ts` sweep. `FULL_AMC` writes no ledger at all — `adjustLoggedHours` no-ops for it, and usage stays a pure on-read aggregate.
- **`assertHoursWithinAllowance` is the one gate on over-cap logging** — call it *before* writing anything. It refuses once the pool is exhausted unless `allowExcess`; with `excessApproval` on it defers to `assertExcessApproved` (below). Unlimited and unmapped pools are a no-op.
- **`SupportHoursExcessRequest` is a permission, not a time entry.** Hitting the cap on an approval-gated pool raises a PENDING row and *still refuses* the log; APPROVED unlocks over-cap logging so the consultant enters their hours normally; REJECTED keeps it blocked and returns the reason. **Approving books nothing** — deliberately, so nobody's time is recorded without them seeing the final figure. There is one live row per pool per period, so a retry names where the decision sits instead of spamming the approver with a second request, and a REJECTED row is not auto-replaced.
- `periodLabel` is the calendar month for `MONTHLY` pools — a new month restores the allowance and must be re-approved rather than riding January's sign-off — and the **`'ALL'` sentinel, never null**, for `FULL_AMC`: Postgres treats NULLs as distinct, so a nullable column in that unique index would stop catching duplicates.
- **Who may decide is checked in the service, not the route.** Only the named `excessApproverId` or a tenant Admin; the endpoints are `StaffGuard` because the client screens are staff-readable, so route-level guarding alone would let any agent sign off someone else's approval. Both the request and the decision notify with a `link` to the pool's own screen — an approver who is a consultant would otherwise have no way to find the client. **The decision is made inline, in `SupportHoursConfig`** — an Approve/Reject radio row on the pool's own screen, right under the setting that demanded it, live only for the named approver or an Admin and only while `PENDING` (everyone else reads the outcome). The separate `ExcessHoursApprovals` panel was **deleted**: it duplicated the same request on both the product and the client screen. `MyExcessApprovals` stays as the Clients-list banner of everything awaiting *this* user, and is only a router to the pool's screen — it decides nothing. Shared hooks live in `components/excessHoursQueries.ts` (`useExcessRequests` / `useDecideExcess` / `latestExcessFor`).
- **`assertMayRaiseTicket` is its sibling on the other side**: an exhausted pool bars the *client* from raising more tickets, but only when `allowTicketsAfterHours` is off for whichever pool governs. Defaults to on, so support does not stop the moment the hours run out. It fires only on the customer self-service path in `create()` — **staff-raised tickets are never gated**, and neither are unlimited or unmapped pools.
- **Consultant dropdowns on client screens are scoped to the product's own agents**, not all staff: `ClientProductPage` and `ClientAssignProductPage` build the `ConsultantGrid` `staff` list from the product's `modules[].consultants` + product-level `consultants` (assigned in the Products screen), rather than querying `/api/users`. Grid cells start empty — the admin picks from that narrowed list.

## Client screen (`CustomerCompaniesPage`)

The client list at `/admin/customer-companies` is a **table**, not a tile grid: a search box over name+code above a `components/ui/table` listing with one column per detail — client name, code, contact person, email, phone, contract scope, tickets, status, then **Actions**. Nullable text cells fall back to an em dash. Deliberately **no logo and no contacts `n/max` column** (a client's headcount lives in the dialog's People list): the wide text cells cap themselves (`block max-w-[…] truncate` + a `title`) and the narrow ones are `w-px`, so the table fits without a horizontal scroll — don't add columns back without re-checking that. **The row itself is inert** — every route out of the page is an explicit icon button, so the row is a plain `<TableRow>` and needs no `role="button"` / `stopPropagation` scaffolding (the old tile did).

- **Three row actions, gated by role:** `Boxes` → `/admin/clients/:id` (Products & consultants) for **all staff** — a consultant is on this screen only to decide an excess-hours request, so it is the one action they get; `Pencil` → the edit dialog and `Trash2` → delete, both **Admin only**.
- **Everything about a client lives in that one dialog**: identity (name, code, max contacts), contact email / contact person / contact number, the logo picker, a **Products & consultants** button routing to `/admin/clients/:id`, and below it a **read-only People list** (a customer's own `CustomerAdmin` manages their users; staff only seed the first admin at creation). There is deliberately no People tab — don't reintroduce one. The dialog stays the only place a client is edited.
- **Logo:** `CustomerCompany.logoUrl` via `POST`/`DELETE api/customer-companies/:id/logo` (multipart — see the Uploads note above). Rendered by `components/CompanyLogo.tsx`, which is `ProductIcon` with a `Building2` fallback and an `assetUrl()` call, since the value is a server path and not a data URL. On **create** there is no id yet, so the picked `File` is held in state and uploaded straight after the company POST returns.
- **`agreedSupportHours` / `supportPeriod*` are dormant data.** They still exist on the model and the DTOs, but `support-hours.service.ts` deliberately does **not** read them: they belong to neither coverage scope, so reporting them showed a customer a pool that governs nothing. Coverage owns this instead — `GET :id/support-usage` answers from the shared contract, and per-product figures come from `CustomerProductsService.productSupportHours`. (`supportAlertThresholdPct` is still live, as the alert threshold.) Don't restore any of them to the form or to the usage maths.

## Client visits & contract draw-down

`ClientVisit` records a client visit against a `CustomerCompany` and a consultant. `api/client-visits` is **Admin-only** (`@UseGuards(JwtAuthGuard, TenantGuard, RolesGuard)` + `@Roles('Admin')`), so `Layout.tsx` filters the Client Visits nav item out for non-admin staff — otherwise agents would follow a link that just 403s.

- **Prisma model vs. table:** the model is `ClientVisit` but carries `@@map("ClientLog")`, and `visitNumber` / `Client.clientVisitSequence` carry `@map("logNumber")` / `@map("clientLogSequence")`. The rename was code-only — the physical table and columns are still the original ones, so no data moved. Don't "fix" the mapping without an `ALTER TABLE`.
- Numbering: `CL-000001`, from `Client.clientVisitSequence` (same pattern as `ticketSequence` / `crSequence`). The prefix is still `CL-` so existing numbers stay valid.
- `consultantName` and `productName` are denormalised at write time so the list needs no join.
- **Creating/editing a visit is a full page** (`/client-visits/new`, `/client-visits/:id/edit` → `ClientVisitFormPage`), not a dialog. Purpose and Description lead the form, then the grid of date / client / product / consultant / hours / status / ticket.
- **There is no visit type and no project link.** Every record is a visit, so the old `visitType` (`ON_SITE`/`REMOTE`/`PHONE`) and the `projectId` field were dropped from the schema, DTOs, filters and UI by `prisma/migrations/manual/client_visit_rename.sql`. The customer-company field is labelled **Client** throughout this module.
- **Statuses are `PLANNED` | `VISITED` | `RESCHEDULE_REQUESTED`** (`VISIT_STATUSES` in both `dto/client-visit.dto.ts` and `pages/client-visits/clientVisitsMeta.ts`). `VISITED` replaced `COMPLETED` as the one status that draws down the contract.
- **Rescheduling is two states, not one.** A consultant reports `RESCHEDULE_REQUESTED` (orange badge, admins notified "needs a new date"); an admin then supplies a date, which flips the row back to `PLANNED` and increments `ClientVisit.rescheduleCount`. The status says where the visit is *now*; `rescheduleCount` carries the history as a separate orange "Rescheduled" badge, so a re-dated visit reads as the normal upcoming visit it is. Consultants cannot set the date at all (`CONSULTANT_EDITABLE` = hours/status/notes) — the admin row action is **Set new date** while a request is open and **Edit visit** otherwise.
- **A visit that hasn't happened yet can't be booked in the past** (`assertScheduleDate`): `PLANNED`/`RESCHEDULE_REQUESTED` must be today or later, while `VISITED` may be back-dated since it records what already happened. Re-dating a `RESCHEDULE_REQUESTED` visit to the date it already has is rejected.
- **A `VISITED` row draws down one pool, never two** (`resolvePool` + `drawDown` in `client-visits.service.ts`, gated by the `DEDUCTING_STATUS` constant): the named product's own AMC/warranty pool (`CustomerCompanyProduct.hoursUsed/visitsUsed` — what the Products screens show) when the customer is on `contractScope = PRODUCT`, otherwise the shared customer contract (`contractHoursUsed`/`contractVisitsUsed`). `contractDeducted` records whether *this row's* draw-down is applied and `deductedCpId` records **where** it landed, so an edit reverses exactly what it applied — even if the product, customer, hours or contract scope changed since — and a status flip or delete reverses exactly once. Any change to hours, status, customer or product must keep that invariant.
- **The form's choices are scoped to the chosen client.** Product comes from `GET :id/purchased-products` (what the customer actually owns) and Consultant from `GET :id/consultants` (that customer's own `CustomerConsultant` rows, deduped by user, narrowed to the picked product plus contract-level rows with `productId=null`). Tickets narrow to the client too. Changing the client resets the other three. The backend enforces the product half: `create`/`update` reject a `productId` the customer doesn't own.
- **`ClientVisitsPanel`** (`pages/client-visits/`) takes a `filter` of `customerCompanyId` / `productId` / `ticketId` (all supported as `GET api/client-visits` query params). It is mounted **only** on the tenant-admin-only **Client Visits** tab of `TicketDetailPage` — it was deliberately removed from `ClientDetailPage` and `ClientProductPage`. Its "Log a visit" button deep-links to `/client-visits/new?…` with those ids pre-filled, and "View all" carries them to the list page as a clearable context filter. The panel hits the Admin-only API — only render it behind an admin check.

## Employee Master & Asset Master

**An employee *is* an internal staff `User`** — there is deliberately no second person table, and no `employees` controller: the Employee Master screens (`/admin/employees`, `/admin/employees/:userId`, tenant-admin only) read and write `api/users`. The employee half is columns on `User`: `employeeId`, department, designation, phone and `managerId` (self-relation `EmployeeManager`, `onDelete: SetNull`).

- `employeeId` is **typed by an admin, not generated**, and unique per tenant (`@@unique([clientId, employeeId])`) — a clash is a `ConflictException` naming who already holds it.
- The manager dropdown lists staff carrying the **`Manager`** role (`assertManager`); see the roles list above for why Admin is not accepted.
- A customer contact is never an employee — every write asserts `customerCompanyId: null`.

**An `Asset` is one physical unit, not an asset type.** `assetId` is the admin-typed code (`LAP-0417`), unique per tenant; `AssetAllocation` joins an asset to an employee `User`. Every fixed vocabulary lives in `assets/allocation-status.ts` — its own file so `AssetsService`, `AssetAllocationsService`, `AssetActivityService` and `ApprovalsService` can import it without a module cycle (the same reason `tasks/task-status.ts` exists) — and **none of them is an option list**, because code branches on every literal.

**Status says only whether the unit is out or back; it used to say three things at once.** `AssetAllocation.status` is `ISSUED | RETURNED` (it was `ISSUED | RETURNED | BROKEN | NOT_RETURNED`), and what the two retired values really meant now lives where it belongs:

- **`returnCondition`** `GOOD | BROKEN` — how it came back, set only while `RETURNED` and defaulted to `GOOD` server-side, so a returned row is never condition-less.
- **`Asset.condition`** `OK | DAMAGED | RETIRED` — the unit's own state, which outlives any one allocation. A `BROKEN` return sets `DAMAGED` (never downgrading a `RETIRED` unit) and an admin clears it back to `OK` on the asset form once repaired. **This is what makes `IN_REPAIR` escapable** — deriving it from the last allocation, as the old model did, was a state nothing could ever leave.
- **`retention`** `RETURNABLE | UNTIL_EXIT` (+ optional `expectedReturnDate`) — the phone or laptop nobody hands in until they leave. An `UNTIL_EXIT` row is **never overdue by definition**, which is the whole point of the flag; deactivating the employee turns their open allocations into the exit-clearance banner on `EmployeeDetailPage`, cleared by the grid's bulk **Return**.
- Re-opening a `RETURNED` row clears `returnCondition` *and* `returnDate`, or a re-issued unit still reads as back on the shelf. `prisma/migrations/manual/asset_allocation_status_rework.sql` maps the old data: both retired statuses meant "still with the employee", so both became `ISSUED` — `BROKEN` additionally damaging its asset, `NOT_RETURNED` additionally getting a past `expectedReturnDate` so it surfaces as overdue.

**An asset's *state* is one value, derived, and shared by both asset screens.** `assetState()` (`pages/assets/assetMeta.ts`) maps a unit to exactly one of `IN_USE | IN_STORE | IN_REPAIR | OTHERS` — **being held wins over being damaged**, since a unit in someone's hands is not sitting in a repair queue — so the four states partition the register exactly once and a row can never read as issued *and* damaged at the same time. The list's State pill and the by-type overview's counts both read it; don't re-derive state at a call site.

- **The invariant the module turns on: at most one *open* allocation per asset**, where open is now exactly `ISSUED`. `assertAssetFree` is the one gate, called before any write (including from the approvals flow above).
- It is a **pre-check + `ConflictException`, not a DB constraint**, on purpose: the containers run `prisma db push` on start, which would drop a hand-added partial index. Don't "harden" it into one.
- **`api/assets` and `api/asset-allocations` are Admin-only, with exactly one hole:** `GET api/assets` also admits `Viewer`, because an agent raising an asset request has to see what is free (`?available=true` filters the register to unheld units). Keep new routes Admin-only. Allocation bulk actions run serially, like the task grid's.

**One allocation grid serves both masters, over the same rows.** `components/AssetAllocationGrid.tsx` takes *either* `employeeUserId` or `assetId` and reads `GET api/asset-allocations?…` — which now includes the live employee projection (`employeeCode` / `employeeName` / `department`), so neither screen joins client-side. That single door is the "mapping": an edit made on the asset screen **is** the record the employee screen shows. `GET api/assets/:id/allocations` and `AssetsService.listAllocations` were deleted with it — don't reintroduce a second read path, and don't make either screen navigate to the other to make a change (`AssetFormPage`'s old read-only table bounced the admin to Employee Master; opening the employee is now an explicit icon in the row). Status is changed in-cell on both, and picking **Returned** opens a portalled `CellPopover` for the date and condition rather than writing a bare status.

**Asset Master is two views of one register, and the flat list is the landing screen.** `/admin/assets` is `AssetListPage` (the table), `/admin/assets/types` is `AssetOverviewPage` (one card per asset type, its count split across the four states); each is one button from the other, `/admin/assets/list` redirects to the former, and every figure on a card links into the list pre-filtered. Both read the same `GET /api/assets` payload — it already carries each asset's open allocation — so a card's count can never disagree with the rows it drills into.

- **Filters sit in a bar of their own above the table, never in the column headings** — the headings are `SortableHead` and sort only. Type and Category are single-select dropdowns unioning the option lists with the values actually in use (plus an `(Unclassified)` entry on the `__none__` sentinel); State is `ASSET_STATES`. **Every selection is held in the URL** (`?type=` / `?category=` / `?state=`), which is also how the overview cards drill in, so a filter arrived at either way reads and clears the same. The list paginates at 25, and its row actions lead with **Allocate** (free) or **Return** (held).
- The register's table deliberately carries **no serial-number column** — it is on the asset form, where one unit is being read, not down a list where it never distinguishes a row.

**`AssetActivity` is the audit trail**, modelled on `TicketActivity` and written best-effort *after* the operation, never inside its transaction (`AssetActivityService.log` swallows failures — a trail that throws must not roll back the allocation it records). It is keyed on the **asset** and carries `employeeUserId`, so one `GET api/asset-activity?assetId=|employeeUserId=` feeds both `AssetActivityTimeline` mountings. **`allocationId` is deliberately a plain column, not a foreign key**: removing an allocation is exactly the event the trail exists to record, so it must not cascade the history away with it.

- **An entry is stamped when the event was *recorded*, never at the business date it refers to.** `issuedDate` / `returnDate` are when the laptop physically changed hands — routinely months before anyone typed it in — so stamping the entry with one produced trails reading "issued 12/03 · added to the register 29/08", an effect before its cause. Use `createdAt`; put the business date in `meta`, where the allocation grid directly above the trail already shows it.
- `prisma/migrations/manual/asset_activity_backfill.sql` reconstructs the trail for everything that predates it, purely from the rows' own stored timestamps and actor columns — every entry carries `meta->>'backfilled' = 'true'` so a rebuilt one is always distinguishable from one the service wrote live. It **clears the table first**, which is both what makes it idempotent and what removes entries phrased in the retired four-status vocabulary. Re-run it after any migration that rewrites allocations with raw SQL — that path does not bump Prisma's `@updatedAt`, so stored timestamps alone can't order those events.

## API conventions

- All routes are prefixed `api/…` (`main.ts` has no global prefix — controllers include it). Staff/admin endpoints live under domain prefixes (`api/products`, `api/customer-companies`, `api/tickets`, …).
- **Customer self-service** endpoints use `my-*` prefixes (`api/my-company`, `api/my-client`, `api/my-team`, `api/my-tasks`, `api/my-change-requests`) and are scoped to `req.user.customerCompanyId`.
- Cross-tenant platform admin under `api/super-admin/*`.

## Git & conventions

- Work happens on release branches (currently `Release_1.0.0`); `main` is the default PR target. Branch before committing if on `main`. Commit only when asked.
- Commit style: short imperative summary of the change set (see `git log`).
- Never fabricate feature results by hand-editing the DB — verify through the real UI/API and clean up test data afterward.
